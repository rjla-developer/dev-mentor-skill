# Mentor Clean

The most dangerous operation in this toolkit. Treat it that way.

Dead code that is actually alive is reached by something a text search cannot see: a
service locator, a reflection call, a filesystem routing convention, a string in a config
file. The whole workflow exists to keep those cases away from an automatic delete.

## Preconditions

All three are mandatory, and the scripts enforce the first two. There is no override flag,
by design.

1. **Clean git working tree.** The cleanup must be the only thing in the diff.
2. **The full suite passes before starting.** Without a green baseline, a failure
   afterwards proves nothing.
3. **The user approved the plan.** Not the idea of cleaning up - this plan, these files.

If the project has no test suite, stop and say so: "There is no suite to verify against.
I can list candidates, but I will not delete on an unverifiable baseline." Then offer to
write the first test.

## Workflow

```
Cleanup progress:
- [ ] 1. Identify candidates
- [ ] 2. Build the plan (scripts/build_cleanup_plan.py)
- [ ] 3. Show the plan; get explicit approval
- [ ] 4. Validate (scripts/validate_cleanup_plan.py)
- [ ] 5. Execute on a dedicated branch
- [ ] 6. Verify; revert on failure
```

### 1. Identify candidates

Use the language's own tooling first - it understands the import graph, which grep does
not: `dart analyze`, `ts-prune` or `knip`, `vulture`, `dotnet build` analyzers,
`ArchUnit`. Read `dead_code_risks` in the stack's registry entry before you believe any of
it.

Write the candidates to a JSON file:

```json
{"candidates": [
  {"path": "lib/legacy/old_parser.dart", "symbol": "OldParser",
   "kind": "class", "action": "delete-file"}
]}
```

Paths are repository-relative with forward slashes. `action` is `delete-file` or
`delete-symbol`.

### 2. Build the plan

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/mentor-clean/scripts/build_cleanup_plan.py" --root . --candidates candidates.json --test-command "<full suite command>" --out cleanup-plan.json
```

`${CLAUDE_PLUGIN_ROOT}` is set by the plugin runtime. The script checks the preconditions, runs the suite, counts inbound references with
`git grep` over tracked files only, and splits candidates into an executable list and a
`requires_human_review` list. It deletes nothing.

Take the test command from the project's own scripts or from the registry's
`testing.commands.full_suite`. Never guess it.

### 3. Show the plan; get approval

Present, per candidate: path, symbol, reference evidence, risk, and - separately - every
entry held back for human review with the reason.

Ask for approval of **the plan**. Then set `"approved": true` in the plan file. Approval
of "clean up dead code" in the abstract is not approval of this plan.

### 4. Validate

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/mentor-clean/scripts/validate_cleanup_plan.py" --root . --plan cleanup-plan.json
```

Run it immediately before executing, even if the plan is a minute old. It re-checks the
tree, the commit, and every file hash, and it rejects the plan if anything moved. If it
exits non-zero, **stop** - the output says exactly what is wrong and what to do. Do not
edit the plan to get past a rejection; rebuild it.

### 5. Execute

```bash
git switch -c chore/dead-code-cleanup
```

Delete only what the executable list names. Nothing else - no drive-by tidying, no import
reordering in files you touched. One commit, referencing the plan.

### 6. Verify

Run the full suite again and report the real result. If it fails:

```bash
git reset --hard HEAD~1
```

Then report which deletion broke it and add that pattern to the stack's
`dead_code_risks` in a pull request, so the next person's plan catches it automatically.

## Never delete without human review

The scripts route these to `requires_human_review` automatically. Know why, because you
will meet cases the patterns miss:

| Pattern | Why it looks dead |
|---|---|
| Generated code (`*.g.dart`, `*.freezed.dart`, `*_pb2.py`, `*.designer.cs`) | Regenerated by a build step; a hand deletion is either undone or breaks the generator |
| Symbols resolved by reflection, DI-by-name, or a string key | No import edge exists to find |
| Public entry points of a library | The consumers are outside this repository |
| Code referenced only from config, tests, or CI | The reference is real but invisible to an import graph |
| Framework convention files (route files, `conftest.py`, `__init__.py`) | Reached by filename, never imported |
| Migrations | Discovered by directory scan, and deleting one rewrites history |
| Code behind a feature flag that is currently off | Off is not dead if someone plans to turn it on |

When a candidate is only referenced from tests, say so plainly: either the code is dead
and its test should go with it, or that test is the last real consumer and deleting the
code is the wrong move. That is a decision for the person who knows the roadmap.

End with the standard three-line status block.
